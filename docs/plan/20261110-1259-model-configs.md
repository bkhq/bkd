# 20261110-1259-model-configs Per-model edit dialogs and custom models in Settings

- **approvedAt**: 2026-11-10 13:05

## Context

- Settings -> Models (`AppSettingsDialog.tsx`): one `EngineCard` per installed engine (virtual engines included, via
  `decorateDiscoveryWithVirtual`). Expanding a card lists its models with a visibility switch and "set default"; no
  per-model details. Hidden models and default model live in `appSettings` per engine.
- Virtual engines (`engines/virtual-engines.ts`, `engine:virtualEngines`) are claude-code + preset env vars
  (base URL, token, fallback model, extra env). They are edited in a form below all engine cards
  (`VirtualEnginesSection`); their cards have no edit control. The API is replace-all `PUT /api/engines/virtual`.
- In practice virtual engines are also used as model variants: the running instance has six, all Fable 5.2 with a
  different `CLAUDE_CODE_EFFORT_LEVEL`. That is what per-model env vars should cover directly.
- Execution: `resolveExecutionModel(engineType, model, profileId)` validates the issue's model against the engine's
  list (`getEngineModels`) and falls back to the default; called from `orchestration/execute.ts`,
  `lifecycle/spawn.ts` (twice) and `orchestration/restart.ts`. Env vars come from `resolveExecEnvVars(profileId,
  projectEnv)` in `issue/utils/helpers.ts` (project env, then virtual-engine env on top).

## Proposal

Data (`appSettings` key `engine:modelConfigs`, JSON `Record<engineType, ModelConfig[]>`):

```ts
interface ModelConfig {
  id: string                    // model id shown in selectors and stored on issues
  name?: string                 // display-name override
  baseModel?: string            // set => custom model; the id passed to the CLI
  envVars: Record<string, string>
}
```

- An entry without `baseModel` overlays the detected model with the same id (name, env vars). An entry with
  `baseModel` is a custom model; its id must not collide with a detected model id.
- Validation like virtual engines: id `^[\w.\-:\[\]]{1,64}$`, unique per engine, env keys `^[A-Z_]\w*$`.

API (`engines/model-configs.ts`, OpenAPI + shared Zod schemas):
- `GET /api/engines/model-configs` -> all engines; `PUT /api/engines/:engineType/model-configs` replaces one
  engine's list (real engine types only; virtual engines keep their own config).
- `getEngineModels()` and the discovery response merge configs into the list: detected models get the overridden
  name; custom models are appended. `EngineModel` gains optional `custom`, `baseModel`, `envVars` for the UI.

Execution:
- `resolveExecutionModel()` keeps validating against the merged list, then maps a custom id to its `baseModel` for
  the CLI. A new `resolveModelEnvVars(engineType, modelId)` returns the entry's env vars; `resolveExecEnvVars()`
  merges project env < model env < virtual-engine env. The issue keeps the configured id, so follow-ups and
  restarts resolve the same way. A deleted custom model falls back to the default, as unknown models do today.

Frontend:
- Each model row in an expanded `EngineCard` gets a pencil button -> `ModelEditDialog`: name, env vars
  (`KEY=VALUE` per line); for custom models also id and base model (select from detected models), plus delete.
  Detected models show "reset" to drop the override.
- Each real engine card gets "Add model" (same dialog, create mode).
- Virtual engine cards get a pencil button -> `VirtualEngineDialog` (name, base URL, token, fallback model, env vars,
  delete); "Add virtual engine" moves next to the engine list. The bottom `VirtualEnginesSection` form is removed.
- Dialogs live in `components/settings/`; i18n keys in `en.json` and `zh.json`.

## Risks

- Env vars from model configs apply to every engine's CLI; a wrong key (e.g. an invalid `ANTHROPIC_*`) breaks
  spawns on that model only. Virtual-engine env still wins for virtual engines.
- Changing a custom model's id orphans issues stored with the old id; they fall back to the default model. The
  dialog warns when editing an existing id.
- Existing virtual engines are untouched; the six Fable effort variants keep working. Moving them to custom models
  is a manual choice (issues bound to those virtual engine ids would fall back).
- `AppSettingsDialog.tsx` is 1700 lines and was changed by another task today; the new UI goes into separate files to
  keep the diff contained.

## Alternatives

- Fold custom models into virtual engines (a virtual engine without base URL = a model variant): no new store, but
  every variant becomes a separate "engine" in the engine picker, which is what clutters the list today. Rejected.
- Per-issue env vars instead of per-model: more flexible, but the user wants presets picked from the model selector.
