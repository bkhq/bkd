## Context

Problem: in loops and multi-project campaigns, a coordinating agent stops on a
question only the user may answer, and the user does not see it in time. The
`bkd` skill already defines the answer — the **decision event** — in
`skills/bkd/references/decision-events.md` (repository `zzci/skills`, not yet
committed there). That file states the flow is agreed and the service is not
built, and that BKD may implement the contract itself. This plan does that.

The contract, in short:

- The coordinator (L1 / multi-repo master) creates one event per question over
  REST at `$BKD_EVENT_URL/events`, with `campaignId`, `ref` (the issue the
  decision concerns), `question`, `context`, `options[]`, `recommendation`,
  `blocks`, `continues` and `notify`.
- The user decides on the event: an `optionId`, a free-form `instruction`, or
  both.
- On `decided` the service sends one follow-up to the `notify` issue:
  `[event-decision eventId={id} campaignId={campaignId}]`. It is a wake signal
  only; the coordinator re-reads the event.
- The coordinator acks with an `outcome` (`applied`) or withdraws an open
  event with a `reason` (`withdrawn`).
- States: `open -> decided -> applied`, or `open -> withdrawn`.

Findings in this repository:

- `GET /api/events` is the SSE stream, and `apps/api/src/events/` plus
  `AppEventMap` mean the real-time bus. The contract's `GET
  $BKD_EVENT_URL/events` would collide if the service sat at `/api`. Mounting
  it at `/api/decisions` gives `BKD_EVENT_URL=$BKD_URL/api/decisions` and
  serves every contract route verbatim (`/api/decisions/events/...`).
- A follow-up reaches an issue through `issueEngine.followUpIssue()`; the
  routing around it (queue while a turn is in flight, `review -> working`,
  pending-message handling) lives in the route handler
  `routes/issues/message.ts` and is not callable from elsewhere today.
- `notes` is the closest global CRUD feature and the template for the route,
  OpenAPI and hook layout.
- The API has no authentication; `decidedBy` is a declared field.
- Latest migration is `0025`.

## Proposal

### Data model (`apps/api/src/db/schema.ts`, one new migration)

`decision_events`

| column | notes |
|---|---|
| `id` | `shortId()` |
| `status` | `open` \| `decided` \| `applied` \| `withdrawn` \| `closed` (check constraint), indexed |
| `campaignId` | text, indexed |
| `ref` | text — issue id the decision concerns |
| `question`, `context` | text |
| `options` | JSON `{ id, label, impact }[]` |
| `recommendation` | JSON `{ optionId, reason }`, nullable |
| `blocks`, `continues` | text, nullable |
| `notify` | JSON `{ type: 'bkd-follow-up', bkdUrl, projectId, issueId }` |
| `decision` | JSON `{ optionId \| null, instruction, decidedBy, decidedAt }`, nullable |
| `outcome` | text, nullable (ack) |
| `withdrawReason` | text, nullable |
| `closeReason` | text, nullable — set when the user closes the event |
| `notifiedAt` | timestamp, nullable — follow-up accepted by the engine |
| `commonFields` | |

### API (`apps/api/src/routes/decisions.ts`, mounted at `/api/decisions`)

```
POST   /api/decisions/events
GET    /api/decisions/events             ?campaignId= &status=
GET    /api/decisions/events/:id
PATCH  /api/decisions/events/:id         only while open
POST   /api/decisions/events/:id/decision   only from open
POST   /api/decisions/events/:id/ack        { outcome }, only from decided
POST   /api/decisions/events/:id/withdraw   { reason },  only from open
POST   /api/decisions/events/:id/close      { reason? }, from open or decided
```

- A transition from the wrong state returns `409`.
- `close` is the user's second action next to `decision`, and an extension of
  the skill contract: the user ends an event without answering it (from
  `open`) or clears one the coordinator never acted on (from `decided`).
  `closed` is terminal, like `applied` and `withdrawn`. Closing sends no
  follow-up; the coordinator sees it on its next scan.
- `decision.optionId` must name one of the event's options; a decision needs
  an `optionId` or a non-empty `instruction`.
- Create validates that `notify.issueId` exists in `notify.projectId`.
- List rows are enriched with the project name and the titles of the `ref`
  and `notify` issues when they resolve locally.

### Notification (`apps/api/src/decisions/notify.ts`)

On `decided`, send `[event-decision eventId=… campaignId=…]` to the notify
issue through the same routing the follow-up route uses. That routing is
extracted from `routes/issues/message.ts` into a shared helper, with the route
as its first caller and behaviour unchanged. The decision is committed first;
a failed notification leaves the event `decided` with `notifiedAt` empty — the
coordinator's scan on its next wake is the contract's safety net, and the UI
marks the event as not delivered with a resend action.

`notify.bkdUrl` is stored but delivery is always local to this BKD instance.

### Real-time

New `AppEventMap` entry `decision-event-updated: { id, campaignId, status }`,
forwarded by the SSE route so the inbox and the sidebar count refresh when an
agent creates, acks or withdraws.

### Frontend (`apps/frontend/src/`)

- Route `/decisions`, global: the decision inbox.
  - *Waiting* — open events, oldest first. Each card shows the question,
    context, options with their impact, the recommended option marked, what is
    blocked and what continues, and links to the `ref` issue and the
    coordinator issue. The user picks an option and/or writes an instruction,
    then decides — or closes the event, with an optional reason.
  - *Decided* — answered, not yet applied by the coordinator; can be closed.
  - *History* — applied (with outcome), withdrawn and closed (with reason).
  - Filter by campaign.
- Sidebar entry (desktop and mobile) with the open count.
- `lib/kanban-api.ts`, `hooks/use-decision-events.ts`, `queryKeys`, SSE
  invalidation.
- i18n keys in `en.json` and `zh.json`.

### Tests

- `apps/api/test/api-decision-events.test.ts`: create and validation; list
  filters; patch only while open; decide by option, by instruction, with an
  unknown option; follow-up sent with the exact wake text; notification
  failure keeps `decided`; ack only from decided; withdraw only from open; close from open and from
  decided, sending no follow-up;
  every wrong-state transition returns 409.
- Existing follow-up tests stay green across the helper extraction.
- Frontend: inbox card and decide flow.

## Risks

- Extracting the follow-up routing touches the busiest message path. It is a
  move without behaviour change, guarded by the existing
  `api-pending-messages` and `api-execution` suites.
- The contract is marked "proposed, not verified" in the skill. Building it
  fixes field names; any deviation found during implementation is reported so
  the skill file can be corrected rather than silently diverging.
- A coordinator on a different BKD instance than the event service is not
  notified (local delivery only).
- `decidedBy` is self-declared while the API is unauthenticated.
- `closed` is not in the skill contract. Closing wakes nobody, so the
  coordinator learns of it only from its scan, and the current skill scan
  lists `open` and `decided` only — a closed event simply drops out of it
  while the work it blocked stays blocked. The skill needs a matching rule (treat as "no decision, drop or
  re-plan the blocked work").

## Scope

About 17 files: schema + generated migration, `decisions/` (service, notify),
route, OpenAPI schemas and routes, follow-up helper extraction, SSE route,
shared types, API client, hook, page and card components, sidebar (2), router,
two i18n files, tests, docs. No dependency changes.

Out of scope:

- BKD opening events on its own from issue state. Per the contract the
  coordinator raises them; BKD stores, shows, and notifies.
- Updating the skill (`zzci/skills`): setting `BKD_EVENT_URL` guidance and
  replacing the "service not built" status. Separate repository.
- Webhook / Telegram notification when an event is opened.
- Cross-instance notification over HTTP using `notify.bkdUrl`.

## Alternatives

- **Mount at `/api/events`** — matches the contract's noun but collides with
  the SSE `GET /api/events`; rejected.
- **Separate service outside BKD** — the skill's original assumption. It
  would need its own UI, storage and a BKD client; BKD already has all three
  and the follow-up is an in-process call.
- **Auto-open a ticket on every settle into `review`** — the previous draft.
  It records stops, not questions: no options, no recommendation, no
  campaign, and it does not match the flow the coordinator already follows.
