## Context

The decision module is a single-purpose "agent asks the human" channel:

- Data: `decision_events` (question/context/options/recommendation/notify/
  decision/outcome, status `open → decided → applied | withdrawn | closed`) and
  `decision_channel_messages` (event → Telegram message id).
- Service: `apps/api/src/decisions/service.ts` — serialize, `transition()`,
  `decideEvent()` (shared by REST and Telegram), `notifyDecision()` which wakes
  the raiser issue via `dispatchFollowUp()` with `[event-decision ...]`.
- Routes: `apps/api/src/routes/decisions.ts` under `/api/decisions`
  (capability probe `contractVersion: 1`, events CRUD,
  `decision/notify/ack/withdraw/close`). Contracts in `openapi/{routes,schemas}.ts`.
- Bus/SSE: `decision-event-updated` (`packages/shared` `SSEEventMap`), consumed
  by `webhooks/dispatcher.ts`, `decisions/telegram/index.ts`, `routes/events.ts`,
  frontend `lib/event-bus.ts`.
- Outbound: `dispatchDecisionEvent()` maps each status to
  `decision.{opened,decided,applied,withdrawn,closed}` and delivers once per
  webhook (dedup key). Interactive Telegram channels are skipped there and
  handled by the Telegram poller (`syncEvent()` posts/redraws with buttons).
- Retention: `decision-event-cleanup` cron soft-deletes non-open events after 1 day.
- Frontend: `/decisions` page (`DecisionsPage`, `DecisionEventCard`,
  `use-decision-events`), sidebar entry in `global-pages.ts`, settings
  `WebhookSection` lists the `decision` event group.
- External contract: the `bkd` skill `references/decisions.md` (separate from
  this repo) tells agents to probe `GET /api/decisions` and use
  `/api/decisions/events`. Agents in the field depend on it.

Gap: an agent can only reach the human by asking a structured question. There
is no way to push an agent-authored message (progress, "deploy finished",
alert, a free-form question) that lands in the inbox and fans out to webhook /
Telegram. Existing webhook events are all BKD-generated (issue/session
lifecycle).

## Proposal

### Model

One `messages` table with a `kind` discriminator replaces `decision_events`.

| Column | Notes |
|---|---|
| `id`, `commonFields` | as today |
| `kind` | `decision` \| `notification` (CHECK) |
| `expects` | `none` \| `reply`. Decisions are always `reply`; a notification chooses |
| `status` | decision: `open/decided/applied/withdrawn/closed` (unchanged); notification `expects=none`: `unread/read`; notification `expects=reply`: `open/replied/applied/withdrawn/closed` |
| `campaignId` | required for decision, optional for notification |
| `source` | JSON `{ projectId, issueId }` — the sending issue (today's `notify`). Required for decisions and for `expects=reply`; optional for `expects=none` |
| `ref` | issue the message concerns (unchanged) |
| `title` | decision: the question; notification: headline |
| `body` | decision: context; notification: Markdown body |
| `level` | notification: `info/success/warning/error`, default `info` |
| `reply` | JSON `{ text, repliedBy, repliedAt }` — the user's answer to a notification with `expects=reply` |
| decision-only columns | `options`, `recommendation`, `blocks`, `continues`, `decision` — unchanged, null for notifications |
| shared reply-flow columns | `outcome`, `withdrawReason`, `closeReason`, `notifiedAt` — used by decisions and `expects=reply` notifications |

`decision_channel_messages` becomes `message_channel_messages` (FK to `messages`).

Migration: generated by `db:generate` for the new tables, plus a custom data
step (`drizzle-kit generate --custom`) that copies `decision_events` →
`messages` (`kind='decision'`, `expects='reply'`, `question→title`,
`context→body`, `notify→source`) and the channel-message rows, then drops the
old tables. IDs are preserved so in-flight decisions and Telegram buttons keep
working.

### Reply flow (decisions and `expects=reply` notifications)

One shared path in the service, generalised from `decideEvent()` /
`notifyDecision()`:

1. User answers — a decision is decided (option + instruction, unchanged); a
   reply-notification gets free-text `reply` → status `replied`.
2. BKD follows up the source issue via `dispatchFollowUp()` with a signal only:
   `[message-reply messageId=… kind=… campaignId=…]` (decisions keep the v1
   `[event-decision …]` signal while the v1 alias is in use).
3. The issue reads the message (`GET /api/messages/items/:id`) and acts, then
   `ack`s with an `outcome` → `applied`. A failed wake leaves the message
   `replied`/`decided`; `POST …/notify` resends.
4. The sender can `withdraw` while open; the user can `close` without answering.

Telegram (interactive channels): reply-notifications are posted like decisions
but without option buttons; replying to the chat message records the reply
(same path the poller already uses for decision replies).

### API — `/api/messages`

- `GET /api/messages` — capability probe
  `{ supported: true, contractVersion: 2, kinds: ['decision','notification'] }`.
- `GET /api/messages/items?kind=&status=&expects=&campaignId=&issueId=` — list.
- `POST /api/messages/items` — Zod discriminated union on `kind`.
  Decision body = today's create body. Notification body:
  `{ kind:'notification', title, body?, level?, expects?, source?, ref?, campaignId? }`
  (`source` required when `expects='reply'`).
- `GET / PATCH /api/messages/items/:id` — PATCH only while open.
- `POST …/:id/decision` (decision), `POST …/:id/reply` (`{ text, repliedBy }`,
  reply-notification), `POST …/:id/{notify,ack,withdraw,close}` (both reply kinds).
  Wrong kind or state → 409.
- `POST …/:id/read` and `POST /api/messages/items/read` (`{ ids? }`, all when
  omitted) for `expects=none` notifications.
- Per-source rate limit on create (30/min per issue → 429).

`/api/decisions/*` is kept as an alias: the same handlers, `kind='decision'`,
v1 field names (`question/context/notify`). Implemented as in-process
forwarding, not an HTTP 30x — agents call it with plain `curl` (no `-L`), and a
redirected POST would break. Frontend `/decisions` redirects to `/messages`.

### Events and outbound delivery

- Bus/SSE event `decision-event-updated` → `message-updated`
  `{ id, kind, expects, status, campaignId }`.
- Webhook event types: `decision.*` unchanged; add
  `message.{sent,replied,applied,withdrawn,closed}` for notifications, each
  state delivered once per webhook (dedup `message.<state>:<id>`). `read` is
  not announced.
- No channel targeting: every channel subscribed to the event receives it.
  Instead the payload carries complete metadata so receivers can route
  themselves:

  ```jsonc
  {
    "event": "message.sent",
    "timestamp": "…",
    "message": { "id", "kind", "expects", "level", "status", "title", "body",
                 "campaignId", "ref", "reply", "outcome", "createdAt", "updatedAt" },
    "source": { "projectId", "projectName", "issueId", "issueNumber", "title",
                "engineType", "model", "issueUrl" },
    "ref":    { "projectId", "issueId", "issueNumber", "title", "issueUrl" } | null,
    "links":  { "messageUrl", "inboxUrl", "apiUrl" },
    "server": { "url", "version" }
  }
  ```

- `WEBHOOK_EVENT_GROUPS` gains a `message` group; the settings UI picks it up.
- Telegram plain channels: level emoji + title + body excerpt + source issue
  link + "awaiting reply" marker when `expects=reply`.

### Frontend

- `/messages` page replaces `/decisions` (redirect kept): tabs All / Decisions /
  Notifications, filter "awaiting me" (open decisions + open reply-notifications),
  unread/awaiting count on the sidebar entry.
- `DecisionEventCard` reused for decisions; new `NotificationCard` (level badge,
  title, Markdown body, source issue link, mark-read, or reply box + close when
  `expects=reply`; shows reply / outcome afterwards).
- Hooks/API client renamed to `use-messages` / `kanban-api` messages functions.
- i18n keys in `en.json` and `zh.json`.

### Retention

- Decisions and reply-notifications: non-open, untouched for 1 day → soft delete (unchanged rule).
- `expects=none` notifications: `read` and untouched for 7 days → soft delete.
- Cron action renamed `message-cleanup`.

## Risks

- **Data migration**: copying rows and dropping `decision_events` is
  irreversible on a live install; open decisions and Telegram mapping must
  survive. Covered by a migration test on a DB seeded at `0028`.
- **drizzle-kit renames are interactive**; new tables + a custom data migration
  avoid the prompt but must be committed with the generated snapshot.
- **Contract drift**: v1 agents keep hitting `/api/decisions`; the alias must
  return the exact v1 shape and keep the `[event-decision …]` wake signal.
- **Notification spam**: mitigated by the per-issue rate limit.
- **Webhook payload shape**: `decision.*` payloads must keep their current
  field names for existing receivers; only `message.*` uses the new envelope.

## Scope

Roughly 30–40 files: schema + 1 migration, `decisions/` → `messages/`
(service, telegram), 2 route files, openapi routes/schemas, dispatcher,
cleanup action, shared types, events route; frontend page, 2 cards, hook,
api client, event-bus, sidebar/global-pages, main routes, settings webhook
section, i18n; ~10 test files; docs.

## Alternatives

1. Keep `decision_events`, add a separate `notifications` table, unify at the
   API/UI layer only — no data migration, but every new kind repeats the pattern.
2. Notifications as webhook passthrough without storage — no inbox, history,
   or reply flow; ruled out by the reply requirement.
3. **Chosen: single `messages` table.**
