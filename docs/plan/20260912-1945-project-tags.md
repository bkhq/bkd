## Context

### What exists today

- `projects` (`apps/api/src/db/schema.ts:31`) has no classification column. The only
  partition is `isArchived`, plus a manual `sortOrder` (fractional index) used for
  drag-and-drop ordering.
- `GET /api/projects` (`apps/api/src/routes/projects.ts:92`) returns every non-deleted
  project for one `archived` flag, ordered by `sortOrder`. There is no filtering,
  pagination, or grouping — the list is always small enough to ship whole.
- `serializeProject()` (`apps/api/src/routes/projects.ts:23`) is the single serialization
  point; `ProjectSchema` / `CreateProjectSchema` / `UpdateProjectSchema`
  (`apps/api/src/openapi/schemas.ts:89-130`) are the single contract point.
- `HomePage.tsx` renders one flat grid of `SortableProjectCard`s plus
  `ArchivedProjectsSection`. No search box, no filter control.
- Project writes come from two dialogs: `CreateProjectDialog.tsx` (flat field list) and
  `ProjectSettingsDialog.tsx` (tabs: general / engine / prompt / envvars / worktrees).
- `useProjects()` / `useArchivedProjects()` (`hooks/use-kanban.ts:60,68`) wrap the two list
  calls; `kanbanApi.getProjects/createProject/updateProject` (`lib/kanban-api.ts:206-230`)
  are the client surface.

### Prior art inside this repo

Issues already have exactly this feature, and it is deliberately denormalized:

- `issues.tag` is one TEXT column holding a JSON array (`schema.ts:54`).
- `parseTags()` / `serializeTags()` in `apps/api/src/routes/issues/_shared.ts:51-71`
  convert between the column and `string[]`, tolerating the legacy single-string form and
  dropping entries longer than 50 chars.
- The shared type exposes it as `tags: string[] | null` (`packages/shared/src/index.ts:43`).
- The UI is a plain comma-separated text input (`CreateIssueDialog.tsx:291`) and badges on
  the card (`KanbanCard.tsx:108`). There is no tag registry, no colours, no rename.

`parseTags` / `serializeTags` are imported only by `routes/issues/create.ts` and
`routes/issues/update.ts`, so they can be relocated cheaply.

### Migration state

Latest migration is `0023_lame_james_howlett.sql`; the next generated file would be `0024`.
Adding a nullable TEXT column is the safest possible schema change, and the startup
self-heal (ENG-011) already reconciles missing columns from the snapshot.

## Proposal

Mirror the issue-tags design on projects: one denormalized column, free-form tags, no tag
registry. Then filter client-side on the dashboard.

### 1. Shared type

`packages/shared/src/index.ts` — add to `Project`:

```ts
/** Free-form classification tags; undefined when the project has none */
tags?: string[]
```

`Project` uses `?:` for every optional field, unlike `Issue`'s `| null`; follow the
surrounding `Project` style rather than the issue one.

### 2. Backend

- **Move the helpers** to `apps/api/src/utils/tags.ts` (verbatim `parseTags` /
  `serializeTags`) and repoint the two issue imports. Reason: `routes/projects.ts`
  importing from `routes/issues/_shared.ts` would create a route-to-route dependency; the
  helpers are pure and already shaped as utilities.
- **Schema**: `projects.tags = text('tags')` (JSON array). Named `tags`, not `tag` — the
  issue column keeps its legacy singular name and there is no reason to inherit it. No
  index: the filter runs in the browser, and a JSON-in-TEXT column cannot be indexed
  usefully anyway.
- **Migration**: `bun run db:generate` produces `0024_*.sql`; the schema change, generated
  `.sql`, `meta/0024_snapshot.json`, and `_journal.json` are committed together.
- **Contract** (`openapi/schemas.ts`): one reusable
  `projectTagsSchema = z.array(z.string().min(1).max(50)).max(20).nullable().optional()`
  added to `CreateProjectSchema` and `UpdateProjectSchema`, plus
  `tags: z.array(z.string()).optional()` on `ProjectSchema`. `null` and `[]` both clear the
  tags, consistent with how `defaultEngine` treats `null`.
- **Routes** (`routes/projects.ts`): `serializeProject()` returns
  `parseTags(row.tags) ?? undefined`; create passes the normalized tags through
  `serializeTags`; update writes `updates.tags` only when `body.tags !== undefined`,
  matching the existing partial-update idiom. Normalization (trim, collapse internal
  whitespace, case-insensitive dedupe keeping first-seen casing) lives in one helper called
  by both handlers, so create and update cannot diverge.

### 3. Frontend

- `lib/kanban-api.ts`: add `tags?: string[]` to the `createProject` and `updateProject`
  payload types.
- `CreateProjectDialog.tsx`: one more field after `description` — a comma-separated `Input`,
  same shape as the issue dialog's tag field.
- `ProjectSettingsDialog.tsx`: the same field in the **general** tab; no new tab.
- `HomePage.tsx`:
  - derive the tag list from the loaded projects (deduped, sorted);
  - render a chip row above the grid when at least one tag exists: `All` plus one chip per
    tag, single-select, held in local `useState` — not persisted, since a sticky invisible
    filter on a landing page is a support burden;
  - filter the active grid by the selected chip;
  - **disable drag reordering while a filter is active** (see Risks);
  - show each project's tags as `Badge`s on the card.
- `ArchivedProjectsSection` is left alone.
- i18n: `project.tags`, `project.tagsPlaceholder`, `project.tagsHint`,
  `project.filterAllTags` in both `en.json` and `zh.json`.

### 4. Tests (RED first)

- `apps/api/test/api-projects.test.ts`: create with tags then read back; update replaces
  tags; `[]` / `null` clears them; a tag over 50 chars or more than 20 tags is rejected
  (400); a project created without tags reads back with `tags` absent.
- `apps/frontend/src/__tests__/`: a focused test that the chip row narrows the rendered
  cards and that `All` restores them.

## Risks

- **Migration discipline** — this adds `0024`; the journal must stay monotonic (ENG-010 was
  a P0 caused by exactly that). Generate it, never hand-write it, and commit schema +
  `.sql` + snapshot + journal in one commit. CI's `Migrations` job catches drift.
- **Drag-and-drop vs. filtering** — the real hazard. `HomePage`'s drop monitor computes a
  fractional key from the adjacent items of the list it renders. Under a filter the
  neighbours are not the true neighbours, so a drop would silently reorder against an
  unrelated project. Mitigation: disable dragging while a filter is active, signalled by the
  cursor rather than an error.
- **Free-form tag drift** — with no registry, `web`, `Web`, and `web ` become three tags.
  Mitigated by the normalization helper above. No rename feature in this scope.
- **Contract surface** — `tags` is additive and optional, so existing clients and the `bkd`
  skill keep working unchanged.

## Alternatives

1. **Normalized `tags` + `project_tags` tables.** Buys tag rename, per-tag colour, ordering,
   and server-side filtering. Costs two tables, a CRUD surface, join queries on every
   project read, and a tag-management UI. Not justified at a scale where the whole project
   list already ships in one response. Revisit if rename or colours are ever asked for; the
   denormalized column backfills into it.
2. **A single `category` field (one-of).** Simpler still, but a tag set of size one *is* a
   category, and the one-of version cannot express "work + rust" — strictly less capable for
   the same amount of UI.
3. **Group instead of filter** — one titled section per tag rather than a chip filter. Reads
   well with few tags, degrades when projects carry several tags (a project shows up in
   multiple sections) and collides head-on with drag-and-drop ordering. The chip filter
   keeps one canonical grid.
4. **Reuse `description` with a convention** (e.g. `#work`). Zero schema change, but
   unparseable, unvalidated, and invisible to any future API consumer.
