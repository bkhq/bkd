# ENG-027 Codex follow-up loses thread config on thread/resume

- **status**: completed
- **priority**: P0
- **owner**: claude
- **createdAt**: 2026-08-13

## Description

`spawnFollowUp` resumes a Codex thread with `{threadId}` only
(`executors/codex/executor.ts` → `protocol.ts` `resumeThread`). The
app-server does **not** inherit the settings of the original `thread/start`;
it falls back to `~/.codex/config.toml` defaults.

Measured against codex-cli 0.144.3 on the same thread:

```
thread/start  → approvalPolicy="never"       sandbox={"type":"dangerFullAccess"}
thread/resume → approvalPolicy="on-request"  sandbox={"type":"workspaceWrite",
                                                      "networkAccess":false}
```

So every follow-up that runs in a fresh process (idle GC, server restart,
next-day continuation) executes sandboxed, without network, and needs an
approval round-trip per command. The user-selected `model` and the working
directory are dropped as well.

Production evidence (`data/db/bkd.db`, ~400 entries, always on follow-up
turns, never on the first turn):

- `bubblewrap is unavailable: no system bwrap was found on PATH ...`
- `当前沙箱缺少 bwrap，普通命令无法运行。我会按规则请求提升权限来继续…`
- `apply_patch 也受当前沙箱缺少 bwrap 影响失败了`

`ThreadResumeParams` in the 0.144.x schema accepts `cwd`, `sandbox`,
`approvalPolicy`, `model`, `modelProvider`, `baseInstructions`,
`developerInstructions` — none of which were being sent.

Secondary defect in the same path: `protocolHandler.sendUserMessage()` calls
`void handler.sendUserMessage(content)` with no rejection handler, so a
failed `turn/start` (RPC error or 30s timeout) silently drops the user's
message and produces an unhandled rejection.

## Scope

- `executors/codex/protocol.ts` — `resumeThread(threadId, params)` sends the
  full `ThreadResumeParams` payload.
- `executors/codex/executor.ts` — `spawnFollowUp` passes
  `buildThreadParams(options)`; `sendUserMessage` rejections are logged.
- `test/codex-protocol.test.ts` — resume payload + send failure coverage.

## Out of scope

- Making `sendUserMessage` synchronously propagate failures to the caller
  (needs an interface change on `SpawnedProcess.protocolHandler`).

## Verification

1. `bun run test:api` green (585 pass / 0 fail)
2. `bun run lint` clean (0 errors)
3. Live protocol check against codex-cli 0.144.3 — resuming with the params
   restores the thread: `approvalPolicy: "never"`,
   `sandbox: {"type":"dangerFullAccess"}`
4. Live end-to-end through the dev API: first turn, kill the app-server,
   then a follow-up (resume path). Logged request:
   `thread/resume {model:"gpt-5.6-sol", cwd:"/tmp/codex-e2e2",
   approvalPolicy:"never", sandbox:"danger-full-access", threadId:...}`.
   The follow-up turn reached the network (`curl https://example.com` → 200)
   and wrote outside the workspace — both impossible before the fix.
