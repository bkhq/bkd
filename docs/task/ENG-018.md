# ENG-018 Extract base64 image data-URIs from engine messages to attachments

- **status**: completed
- **priority**: P1
- **owner**: roy
- **createdAt**: 2026-05-22

## Problem

Image-generating models (e.g. `nano-banana-pro-preview` via a virtual engine)
return the image inline as a markdown base64 data-URI in the assistant text.
bkd stores the whole string in `issues_logs.content` (observed: a single 1.36 MB
row) and the chat renders it as highlighted markdown *source* (MarkdownContent
uses Shiki `codeToHtml`), so the user sees a giant base64 blob — no image — and
every `/logs` fetch + SSE event carries the megabytes.

## Approach (B — approved)

On persist, extract `data:image/...;base64,...` payloads from a log entry's
content, decode + store each as a file, and replace the data-URI in the stored
content with a short URL reference. The content row stays small; the image is
served from disk.

Decisions:
- Reuse the existing `attachments` table + uploads dir + serving route (it
  already links to a `logId` and has a cleanup job), linking the extracted
  image to its log entry.
- Frontend: render image references in chat as real `<img>` (MarkdownContent
  currently only highlights source). Also render legacy `data:` image URIs so
  the existing 1.36 MB message displays.

## Scope

- api: a helper that scans/extracts data-URIs → attachment rows + files, wired
  into the log persistence pipeline (assistant messages + tool results).
- frontend: image rendering in `MarkdownContent` (or LogEntry) for attachment
  URLs and `data:` URIs.
- tests: extraction (data-URI → file + rewritten content), size reduction.

## Verification

- New image messages persist a small content row + an attachment file; chat
  shows the image.
- `bun run test`, `bun run lint`, tsc clean.

## Result (verified)

- `engines/issue/pipeline/extract-images.ts`: `extractImageDataUris(issueId,
  content)` decodes each `data:image/<t>;base64,…` to `data/uploads/`, inserts an
  `attachments` row, and rewrites the data-URI to
  `/api/projects/<pid>/issues/<iid>/attachments/<id>`. Wired as pipeline **order
  5** (before persist=10 and SSE=100), so the DB row and SSE payload carry the
  small URL.
- Frontend `MarkdownContent`: renders image markdown (`data:image/…`, `/api/…`,
  `http(s)`) as `<img>` (it previously only Shiki-highlighted source), so both
  new attachment URLs and legacy inline data-URIs display.
- tests: `extract-images.test.ts` (data-URI → attachment file + rewritten,
  smaller content; no-op without images).

Verification:
- `bun run test:api` 539 pass / 0 fail; `bun run test:frontend` pass;
  `bun run lint` 0 errors; tsc clean (api + frontend).

## Notes

- Extraction applies to newly persisted entries; the pre-existing 1.36 MB
  message still has the inline data-URI in its row but now renders as an image
  via the frontend change.
- Extracted images live under `data/uploads/` and are subject to the existing
  upload-cleanup job (7-day retention) — same as user attachments.
