# REL-002 Publish lode-compatible signed release assets

- **status**: completed
- **priority**: P1
- **owner**: roy
- **createdAt**: 2026-08-24 00:00

## Description

Make GitHub Releases consumable by lode's GitHub source adapter.

lode selects an asset by exact filename (`src/manifest.rs:691`), so the current
version-bearing name `bkd-app-v{version}.tar.gz` cannot be used. Publish a fixed
`bkd-app.tar.gz` and keep uploading the legacy name with identical bytes so already
deployed launchers keep updating during the transition.

Acceptance criteria:

- `release.yml` uploads `bkd-app.tar.gz` plus the legacy `bkd-app-v{version}.tar.gz`.
- `checksums.txt` covers both names and `sha256sum -c` passes in CI before publishing.
- Assets are ed25519-signed via `lode-cli sign` and uploaded with the signature as the
  asset `label` when `LODE_SIGNING_KEY` is set; unsigned upload otherwise.
- `.github/workflows/launcher.yml` is deleted.

## Notes

See PLAN-018.

Completed 2026-08-24.

- `release.yml` builds `bkd-app.tar.gz` (the lode selection key) and a byte-identical
  `bkd-app-v{version}.tar.gz` for pre-lode launchers; `checksums.txt` covers both and is
  verified before publishing.
- Release creation moved from `softprops/action-gh-release` to `gh` because the asset
  `label` (where lode reads the signature) is only settable via `gh release upload
  "$TAG" "file#label"`. Creation is idempotent — an existing release is reused.
- Signing uses `lode-cli sign` pinned to `LODE_VERSION`, and falls back to unsigned
  uploads when `LODE_SIGNING_KEY` is unset.
- Verified against the real `lode-cli` v0.1.0: the signature binds the version WITHOUT
  the leading `v` (the GitHub adapter strips it), and `lode-cli sign` prints a report
  rather than a bare signature — the workflow signs with `${VERSION#v}` and extracts the
  `sig:` field. Upstream's documented `sig=$(lode-cli sign ... --version "$TAG")` would
  produce an unusable label on both counts.
- `.github/workflows/launcher.yml` deleted.

Follow-up 2026-08-24 — signature verification deferred, operator files published:

- Every release now also uploads `bkd.lode.toml` (ready-to-use config), `DEPLOYMENT.md`
  (the guide) and `migrate-to-lode.ts`, so operators install and migrate straight from the
  release page without a repo checkout. Release notes carry a copy-pasteable quick start.
- Signing remains wired but inert (no `LODE_SIGNING_KEY` set), and the shipped configs use
  `require_signature = "off"`. Integrity is unaffected: lode verifies the sha256 of the
  downloaded bytes against the GitHub asset digest under every policy
  (`install.rs:462` `verify_integrity`, outside the `require_signature` branch).

Follow-up 2026-08-24 (asset renamed, legacy copy dropped) — **supersedes the dual-upload
decision in the Description and the first two notes above**:

- The release asset is now `bkd-server.tar.gz`, and the byte-identical
  `bkd-app-v{version}.tar.gz` copy is no longer published.
- Reason: the compatibility copy was the hazard, not the fix. Pre-lode BKD selects an
  update with `name.startsWith('bkd-app') && name.endsWith('.tar.gz')`
  (`checker.ts:36-40` at cd9fd17) and the pre-lode launcher with
  `/^bkd-app-v\d+\.\d+\.\d+\.tar\.gz$/` (`launcher.ts:49`). Both matched the copy, so an
  un-migrated install would have downloaded a lode-only package and then run it with no
  supervisor and no way to update itself.
- Under the new name neither selector matches, so un-migrated installs report
  "up to date" and keep running what they have. Binary-mode installs were already
  excluded — they filter out `.tar.gz` assets.
- `scripts/package.ts` now defaults to the same fixed, version-free name, and a test
  asserts the configured asset can never match either legacy pattern again.
