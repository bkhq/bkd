# REL-005 Close the release window where latest has no assets

- **status**: completed
- **priority**: P0
- **owner**: roy
- **createdAt**: 2026-08-27 00:00

## Description

lode instances report `update check: manifest: release "0.0.98" has no assets`.

The release is published before its assets exist. For v0.0.98 the release became
`/releases/latest` at 18:12:24Z while `bkd-server.tar.gz` only landed at 18:14:01Z — a
97-second window in which lode resolved a release it could not use
(`manifest.rs:446`). The release was cut with `gh release create`, which publishes
immediately; the workflow then took its "already exists — reusing it" branch and uploaded
assets afterwards.

The error is also sticky: lode clears `last_error` only when an update commits
(`supervisor.rs:2378`), and an update check failure is recorded as non-fatal via
`note_error` (`supervisor.rs:1859`) without changing `status`. A transient window
therefore leaves a red error in the BKD settings UI indefinitely, on an install that is
otherwise healthy.

Acceptance criteria:

- The release workflow never exposes an asset-less release as `latest`: create (or
  demote to) a draft, upload assets, then publish.
- Cutting a release by hand does not reintroduce the window — the documented command
  creates the tag only and lets CI own the release.
- A non-fatal `last_error` is not presented as a broken install while the supervisor
  status is healthy.
- Release notes and the deployment guide describe the supported way to cut a release.

## Notes

Follows PLAN-018.

Completed 2026-08-27. Two independent defects, both reproduced against lode v0.1.0 and
the live releases.

**1. The release published before its assets existed.** For v0.0.98 the release became
`latest` at 18:12:24Z and the assets landed at 18:14:01Z — 97 seconds during which lode
resolved a release with nothing to install. The workflow now creates (or demotes an
existing release to) a draft, uploads, and only then publishes with `--draft=false
--latest`; drafts are excluded from `latest`, so the window is gone. Cutting a release by
hand with `gh release create` reopens a smaller window, so the documented command creates
the tag only and lets CI own the release.

**2. The settings panel never reflected a requested update.** `UpgradeStatus` carried no
pending-request field, and the status query only polled while lode's status was
`updating` / `rolling-back` / `starting`. The single invalidation after the POST landed
about a second before lode picks the request up, so it observed `running`, stopped
polling, and the panel sat there showing an enabled Update button while the update ran to
completion in the background — indistinguishable from "the button does nothing".

The status payload now exposes lode's `target`, which is set from the moment the request
is written until lode consumes it, and the query polls on that. Verified end to end:
`target` was visible at 0.5s and 1.0s while `status` was still `running`, the API went
away during the version swap, and the requested version landed and committed as
last_good. The panel also flags when the running version no longer matches the build that
served the page, with a reload action.

The backend and the SDK usage were never at fault: a request written with
`Lode.requestUpdate()` was picked up, downloaded, installed and restarted within ten
seconds in the first reproduction.

Follow-up 2026-08-27 (panel usability):

- The Update button was gated on a cached `hasUpdate`, so it stayed disabled until lode
  advertised a version — and the panel only learned about that on a reload, which is why
  it appeared to need a restart first. It is now always enabled: writing `target=latest`
  makes lode resolve the channel immediately, which is the only on-demand check the
  contract offers (lode advertises on its own 5-minute schedule otherwise). Verified
  against lode v0.1.0 that requesting the running version is a clean no-op — `target` was
  consumed within 2s, the child pid never changed, no restart and no error
  (`supervisor.rs:1962` clears the request when the resolved version equals the running
  one).
- The status query now also polls slowly (15s) while the panel is open, so a version lode
  advertises on its own shows up without reopening the dialog or reloading.
- `upgradeRestart` still read "Restart to upgrade" / "重启升级", a label from the old flow
  where restarting *was* the apply step. Under lode it only relaunches the current
  version, so it now reads "Restart" / "重启服务". Verified: the request bumps
  `restart_nonce`, lode relaunches the child (new pid) and `current` is unchanged.
