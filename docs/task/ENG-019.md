# ENG-019 Normalize assistant image content blocks (Bifrost) to attachments

- **status**: completed
- **priority**: P1
- **owner**: roy
- **createdAt**: 2026-05-22

## Problem

Image-generating models (e.g. `nano-banana-pro-preview`) now return the image
as a native Anthropic `image` content block (`type: 'image'`,
`source.type: 'base64'`, ~1.9 MB jpeg) instead of a markdown `data:image`
data-URI embedded in assistant text. This happened after switching the upstream
gateway from New API (returned the image as a text data-URI) to Bifrost (returns
a proper `image` block).

The claude normalizer's `parseAssistant` (`normalizer.ts`) handles `text`,
`thinking`, `tool_use`, and server tool blocks but has no `image` case, so an
assistant message that contains only an image block produces zero entries — the
message is dropped entirely. The chat shows nothing and no attachment is created
(verified on issue `ekfu3nwn`: no assistant-message rows, no attachment, no
`extract_image_failed` log).

This is not caused by ENG-018; ENG-018 extracts `data:image` URIs from text,
which Bifrost no longer sends.

## Approach

Bridge the new `image` blocks back into the path ENG-018 already handles: in
`parseAssistant`, emit an `assistant-message` whose content is a markdown
data-URI (`![image](data:<media_type>;base64,<data>)`) for each base64 `image`
block. The existing extract-images stage (order 5) then decodes it to an
attachment file and rewrites the content to a small served URL before persist
(order 10) and SSE (order 100); the frontend `MarkdownContent` already renders
attachment/`data:` image markdown as `<img>`.

## Scope

- `normalizer-types.ts`: add an `image` variant to `ClaudeContentItem`.
- `normalizer.ts`: handle base64 `image` blocks in `parseAssistant`.
- tests: image block → data-URI assistant-message entry.

## Verification

- New image messages produce an assistant-message that extract-images turns into
  a small content row + attachment file; chat shows the image.
- `bun run test:api`, lint, tsc clean.

## Result

- `normalizer.ts`: assistant `image` content blocks (`source.type === 'base64'`)
  are emitted as an `assistant-message` carrying `metadata.imageData`
  (`{ mediaType, base64 }`) — no data-URI string round-trip.
- `extract-images.ts`: shared `storeImageBytes()` writes the attachment;
  `rewriteEntryImages()` handles both `metadata.imageData` (image blocks) and
  inline `data:image` URIs (ENG-018 text path), so both funnel through one
  storage path.
- Tests: normalizer image-block → metadata; extract-images metadata → attachment
  URL with base64 dropped. `test:api`, lint, tsc clean.

Gateway caveat (out of scope, not BKD): with Gemini image models, the upstream
returns the image only on the non-streaming `generateContent` call
(`streamGenerateContent` is unsupported / yields no image). CLI engines always
stream, and the gateways tested (Bifrost, LiteLLM) do not surface the image in
their Anthropic streaming path — so this normalizer fix only takes effect once a
gateway delivers a real `image` block (or `data:image` text) over the stream.
