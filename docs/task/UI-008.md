# UI-008 Render chat markdown with streamdown instead of Shiki highlighting

- **status**: completed
- **priority**: P2
- **owner**: cd
- **createdAt**: 2026-09-09 03:36

## Description

Assistant messages and tool results in the issue chat are rendered by
`MarkdownContent`, which feeds the raw text to Shiki with `lang: "markdown"`.
Shiki is a TextMate-grammar syntax highlighter: it colours the markdown
source but never parses it, so headings, emphasis, lists and links show up as
literal `#`, `**` and `[]()` markup. Real markdown rendering only exists in
the "view message" dialog and the file browser (`MarkdownRenderer`,
react-markdown + remark-gfm).

Replace the chat renderer with `streamdown` (vercel/streamdown), a
react-markdown-compatible component built for streaming: it parses per block,
repairs unterminated constructs (`remend`) while a message is still arriving,
sanitizes output (rehype-sanitize + rehype-harden) and styles with Tailwind
utilities on shadcn CSS variables, which matches this frontend.

Proposal:

- Add `streamdown` to `@bkd/frontend`. Do not add `@streamdown/code`: it pins
  `shiki@^3`, which would ship a second Shiki copy and bypass the
  `shiki-slim` Vite plugin. Route fenced code through the existing
  `ShikiCodeBlock` (Shiki 4 slim bundle) via `components={{ pre, code }}`.
- Rewrite `MarkdownContent` around `<Streamdown mode="streaming">`. Pass
  `isAnimating` for entries that are still streaming (no `messageId`),
  `controls={false}` and `lineNumbers={false}` to keep chat compact, and a
  `urlTransform` that keeps `/api/...` and `data:image/...` sources so
  attachment images keep rendering.
- Remove the now-dead pieces: table space-padding preprocessor, the
  `splitImages` regex extraction, the DOMPurify call in `MarkdownContent`,
  and the `.markdown-shiki` CSS block.
- Add `@source "../../../node_modules/streamdown/dist/*.js"` to `index.css`
  so Tailwind v4 emits the utilities streamdown uses.
- Out of scope: `MarkdownRenderer` (files + view dialog) stays on
  react-markdown; switching it is a possible follow-up once the chat path is
  proven.

Acceptance criteria:

- Headings, emphasis, lists, links, tables and inline code in assistant
  messages render as HTML in the chat; fenced code is highlighted by the
  existing Shiki 4 bundle.
- A partially streamed message (unterminated `**`, list item or code fence)
  renders without flicker or crash and settles once the final entry arrives.
- Tool-result markdown in `ToolItems` uses the same component.
- Only one copy of Shiki in the production bundle (`vendor-shiki` chunk
  unchanged in language/theme set).
- New vitest cases for `MarkdownContent` pass, followed by the frontend
  suite, lint, typecheck and `bun run build`.

## Notes

- Requested by the user on 2026-09-09 after asking why SSE-rendered markdown
  was never converted.
- Branch `feat/ui-008-streamdown`, forked from `release` at the user's request.
- Dropped from the proposal: keeping `data:image/...` sources. streamdown's
  sanitize layer blocks them regardless of `urlTransform`, and the server
  already extracts inline base64 images to attachments
  (`pipeline/extract-images.ts`), so only legacy logs are affected.
- streamdown renders `strong` as `<span data-streamdown="strong">`, not
  `<strong>`; tests target the data attribute.
- Fenced code is routed through the `inlineCode` / `code` split: with
  `inlineCode` set, streamdown sends only block-level code to `code`, so
  `ShikiCodeBlock` (Shiki 4 slim bundle) handles fences without
  `@streamdown/code`. The lockfile still holds a single `shiki@4.4.3`.

- complete: Focused tests and the frontend suite passed; lint, typecheck and
  build verified.
- streamdown 2.6.0: peer React ^18 || ^19, deps marked/unified/remark-gfm/
  rehype-sanitize/tailwind-merge, ~110 KB unpacked; react-markdown already
  pulls most of the unified pipeline, so the marginal bundle cost is small.
