# ENG-025 Resolve auto/unknown model to engine default at execution time

- **status**: completed
- **priority**: P1
- **owner**: claude
- **createdAt**: 2026-08-02

## Description

When an issue executes with `model = 'auto'` or a model id that no longer
exists in the engine's model list (e.g. removed catalog entries such as
`claude-opus-4-8`), the orchestration layer currently passes `undefined`
(for auto) or the stale id through to the CLI. Requirement: resolve both
cases to the engine's default model (`isDefault` in the probed model list)
before spawning.

## Scope

- New `apps/api/src/engines/model-resolver.ts`:
  - `pickExecutionModel(models, model)` — pure selection logic
  - `resolveExecutionModel(engineType, model, engineProfileId?)` — async
    wrapper over `getEngineModels()` (cached probe data); pass-through
    (legacy `'auto'` → undefined) when the model list is unavailable/empty
    or when the issue runs a virtual engine profile (their catalogs come
    from the provider, not the probe)
- Apply at the four orchestration sites: `orchestration/execute.ts`,
  `orchestration/restart.ts`, `lifecycle/spawn.ts` (retry + follow-up)
- DB keeps the user's raw selection (`auto` stays `auto`); only the
  spawned process gets the resolved model. Log when a switch happens.
- Tests: `apps/api/test/model-resolver.test.ts` (pure fn + cache-seeded
  wrapper)

## Out of scope

- Validating models for virtual engine profiles (provider-side catalogs)
- Executor-level `'auto'` guards (kept as final safety)
