# ENG-035 Probe engines on demand only, never on a timer

- **status**: completed
- **priority**: P1
- **owner**: roy
- **createdAt**: 2026-08-30 00:00

## Description

Probing spawns the engine CLIs, and for Claude that includes
`claude auth status --json`, which touches the rotating OAuth credential. ENG-034
removed the per-execution probe; the 6-hour DB TTL (`PROBE_DB_TTL_MS`) was the
remaining timer, forcing at least four live probes a day whether or not anything
had changed.

Persisted probe results now never expire. A live probe happens only when it is
actually wanted:

- first install — no rows stored yet
- a recorded binary has vanished (`probeBinariesMissing`, e.g. the CLI moved)
- the operator presses "probe engines" in settings (`POST /api/engines/probe`)

Acceptance criteria:

- `getProbeResults()` serves stored results regardless of age.
- Nothing re-probes on a schedule.
- Tests assert the stored copy survives an arbitrary age and a missing timestamp.

## Notes

Completed 2026-08-30. Deleted `PROBE_DB_TTL_MS` and the "rows without a timestamp
are expired" rule from `db/helpers.ts`. The timestamp is still written, unread, so
the last probe time stays inspectable.

This deliberately reverses ENG-029, which added the TTL so a CLI upgrade's new
model catalog would be picked up. The exposure is narrower than it sounds and was
accepted knowingly: `claude-code`'s catalog is static in code and always overlaid
(`withFreshStaticModels`, `getEngineModels`), and virtual engines fetch models from
their provider — so only Codex can go stale, and the manual probe button
(`AppSettingsDialog.tsx:937`) fixes it in one click.

`test/probe-cache.test.ts` was inverted accordingly: the two tests that asserted
expiry now assert persistence, plus a case for "nothing probed yet".
