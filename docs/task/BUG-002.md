# BUG-002 Worktree creation fails on repos without main/master

- **status**: completed
- **priority**: P1
- **owner**: claude
- **createdAt**: 2026-05-20

## Description

`resolveMainBranch` in `apps/api/src/engines/issue/utils/worktree.ts` only
recognised four branch names (`origin/main`, `origin/master`, `main`,
`master`) and threw if none existed. Repos using a `release → develop →
feature/*` model (e.g. `ttpos-server-go`, whose `origin/HEAD → origin/release`)
have no main/master, so:

```
resolveMainBranch throws
  → createWorktree throws
  → orchestration try/catch swallows it (worktree_creation_failed_fallback_to_base)
  → workingDir silently falls back to the shared repo directory
  → the agent runs un-isolated, directly on the project repo
```

Introduced by commit `6506bc1`, which deliberately refused to fall back to
`HEAD`.

### Acceptance Criteria

- [x] Worktree creation resolves the repo's real default branch via
  `git symbolic-ref refs/remotes/origin/HEAD`
- [x] Common names (`release`, `develop`, …) added to the candidate list
- [x] Falls back to `HEAD` as a last resort instead of throwing (a HEAD-based
  worktree is still isolated from the shared checkout)
- [x] Worktree-creation failures emit a visible diagnostic log entry on the
  issue instead of failing silently
- [x] Regression tests for non-main default branch + HEAD fallback

## Notes

Fix:

- **Part 1+2** — `resolveMainBranch` → `resolveStartPoint` in
  `worktree.ts`: query `origin/HEAD`, extend candidate list, fall back to
  `HEAD`. Throws only on a repo with no commits at all.
- **Part 3** — the three orchestration fallbacks (`execute.ts`,
  `restart.ts`, `spawn.ts`) now emit a `worktree_fallback` diagnostic log
  so an un-isolated run is visible to the user, not just in server logs.

Tests: `apps/api/test/worktree.test.ts` — release-branch repo + HEAD
fallback cases.
