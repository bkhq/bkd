# ENG-014 Virtual engines: dynamic model discovery via provider /v1/models

- **status**: completed
- **priority**: P2
- **owner**: roy
- **createdAt**: 2026-05-22
- **extends**: ENG-013

## Problem

A virtual engine's model was typed manually; if the id is not present on the
gateway it fails (gateway returns 503 / no channel). The gateway
(`aigw.fr.ds.cc`, newapi) exposes an OpenAI-format `GET /v1/models` and speaks
the Anthropic `/v1/messages` protocol (verified: `gemini-3.5-flash` over
`/v1/messages` → 200). So models should be fetched from the provider, like the
real engines, leaving the user to configure only **name + link info**.

## Approach (approved)

- VirtualEngine gains first-class `baseUrl` + `authToken` fields (mapped to
  `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN`); `model` becomes an optional
  fallback default. Advanced free-form `envVars` kept (collapsible in UI).
- Server fetches `{baseUrl}/v1/models` (fixed path; OpenAI `{data:[{id}]}`),
  `Authorization: Bearer <token>`, base normalized (`…/v1/models`), per-fetch
  timeout, results mapped to `EngineModel[]` and placed in
  `discovery.models[virtualId]`. In-memory TTL cache; refreshed by
  `POST /api/engines/probe` and cleared on `PUT /api/engines/virtual`.
- Fallback: fetch fails/empty → optional manual `model`, else empty (engine
  default).
- Frontend create/chat model dropdowns already read `discovery.models[...]` →
  no change needed there; gateway models appear automatically.
- SSRF: accepted (admin-configured URL, models-only GET, timeout, no redirect).

## Scope

- shared: `VirtualEngine.baseUrl`, `.authToken`.
- api: `virtual-engines.ts` (env merge + model fetch + cache), `engines.ts`
  (schema + cache invalidation on probe/PUT).
- frontend: `AppSettingsDialog` VirtualEnginesSection (Base URL + Token fields +
  advanced env), i18n.
- tests: base-URL normalization, env merge, model-fetch parsing (mocked fetch).

## Verification

- `bun run lint`, `bun run test`, tsc clean.
- Manual: configure a virtual engine with the aigw base+token, confirm the
  create dialog model dropdown lists gateway models and an issue runs.

## Result (verified)

- shared: `VirtualEngine.baseUrl` + `.authToken`.
- `virtual-engines.ts`: validate baseUrl; `resolveProfileEnvVars` merges
  baseUrl/authToken → `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` (dedicated
  fields win over advanced envVars); `fetchVirtualEngineModels` (GET
  `{base}/v1/models`, Bearer, 8s timeout, redirect:error, OpenAI `{data:[{id}]}`
  → `EngineModel[]`); 10-min TTL `modelCache` + `clearVirtualModelCache`;
  `decorateDiscoveryWithVirtual` populates `models[id]` from discovery, falling
  back to optional `model`.
- `engines.ts`: schema adds `baseUrl`(url)/`authToken`; `PUT /virtual` clears
  cache (via `setVirtualEngines`); `POST /probe` clears cache.
- frontend: `VirtualEnginesSection` now has Base URL + Token (password) fields;
  default model + extra env moved under an `Advanced` `<details>`. i18n en+zh.
- tests: `api-virtual-engines.test.ts` — baseUrl/authToken persist + validation,
  env-merge precedence, `fetchVirtualEngineModels` mapping + auth + non-OK
  fallback (mocked fetch).

Verification:
- `bun run test:api` 519 pass / 0 fail; `bun run test:frontend` 39 pass;
  `bun run lint` 0 errors; tsc clean (api + frontend).
- Live: against `https://aigw.fr.ds.cc`, `/api/engines/available` returned 6
  discovered models for the virtual engine (gemini/gemma family). Backward
  compatible with the existing envVars-based config (fetch falls back to
  `envVars.ANTHROPIC_BASE_URL`).

## Diagnosis of original report

The manually-typed model was not present on the gateway (gateway lists
gemini/gemma, no claude models) → 503 / no channel. The gateway *does* speak
the Anthropic `/v1/messages` protocol (verified `gemini-3.5-flash` → 200), so
picking a discovered model fixes it.
