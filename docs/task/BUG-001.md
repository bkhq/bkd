# BUG-001 Fix OpenCode hanging without error on quota exhaustion

- **status**: completed
- **priority**: P1
- **owner**: opencode
- **createdAt**: 2026-05-09 10:30

## Description

When using OpenCode as the AI engine, if the API quota is exhausted or the engine encounters other fatal errors, the process hangs indefinitely without reporting any error to the user. The UI shows a perpetual "thinking" state instead of failing gracefully.

### Acceptance Criteria

- [x] OpenCode prompt calls have a reasonable timeout
- [x] When timeout occurs, an error message is emitted to the user
- [x] The process state transitions to 'failed' instead of staying 'running'
- [x] Existing stall detection still works for other engines
- [x] Stderr fatal errors (quota, auth, network) are detected and trigger logical failure

## Notes

Investigation findings:

1. **Root cause**: In `apps/api/src/engines/executors/acp/protocol-handler.ts`, `runPrompt()` calls `this.connection.prompt()` without any timeout. When OpenCode's internal API call fails (quota exhausted, network error), the ACP SDK's `prompt()` method may never resolve or reject — the process stays alive but silent.

2. **Current mitigation**: The GC sweep (`apps/api/src/engines/issue/gc.ts`) has a 3-tier stall detection:
   - T+3min: detect stall (non-destructive)
   - T+5min: send interrupt probe
   - T+7min: force kill
   But this means users wait up to 7 minutes with no feedback.

3. **Stderr handling**: OpenCode may write quota errors to stderr, but stderr is consumed as generic error messages without specific pattern detection.

4. **Files involved**:
   - `apps/api/src/engines/executors/acp/protocol-handler.ts` — add prompt timeout
   - `apps/api/src/engines/executors/acp/normalizer.ts` — ensure timeout errors are properly normalized
   - `apps/api/src/engines/issue/constants.ts` — may need ACP-specific timeout constants
