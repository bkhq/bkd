# ENG-010 Fix non-monotonic migration journal (0020) + harden fix-db

- **status**: completed
- **priority**: P0
- **owner**: claude
- **createdAt**: 2026-05-16

## Symptom

`/app/bkd` (v0.0.73): server won't boot normally; `./bkd fix-db` →
`[fix-db] Repair failed at 0006_flippant_typhoid_mary: no such column:
priority`. This is class-wide: any DB upgraded from a pre-0020 build is
affected, not just this deployment.

## Root cause (proven)

Drizzle's bun-sqlite migrator (`sqlite-core/dialect.cjs:679`) decides what to
apply by a **timestamp watermark**, not by hash:

```
last = SELECT ... FROM __drizzle_migrations ORDER BY created_at DESC LIMIT 1
apply migration IFF  !last || Number(last.created_at) < migration.when
```

`_journal.json` is **non-monotonic at entry 0020**:

| idx | tag | when |
|----|------|------|
| 19 | 0019_drop_whiteboard | 1778976000000 |
| 20 | 0020_sloppy_paibok | **1778874927040** ← ≤ 0019 |

Entries 0–19 are strictly increasing; only 0020 regresses (it was generated
with a real `Date.now()` while 0014–0019 were hand-set to rounded future
values — see ENG-009 "0014–0019 added as raw SQL").

Consequence chain (every DB that recorded 0019):

1. `__drizzle_migrations` watermark = `MAX(created_at)` = 1778976000000.
2. Normal startup `migrate()`: `1778976000000 < 1778874927040` is **false**
   → **0020 is permanently skipped**.
3. 0020 adds `projects.default_engine` / `projects.default_model`; the Drizzle
   schema expects them → `verifySchema()` (`db/index.ts`) → `process.exit(1)`
   → server can't boot.
4. User runs `fix-db`. `repair.ts` uses a *different* algorithm — per-file
   sha256 vs `__drizzle_migrations`. The ENG-009 history re-alignment changed
   `0006`'s file content, so its current hash (`9522561548aa…`) ≠ the recorded
   old-content hash (`c830c530…`). Repair re-executes the destructive 0006 on
   a DB where `priority` was dropped long ago →
   `UPDATE issues SET tag=…priority…` → `no such column: priority`, which is
   not in `TOLERATED` → abort.

Evidence: `/app/bkd` DB has 20 `__drizzle_migrations` rows; 19 hashes match
current files, only `0006` mismatches (re-aligned), `0020` absent. Schema
already has `tag`, lacks `priority` (old 0006 ran historically).

So the true root cause is the **broken journal `when` for 0020**; the
`fix-db` crash is a fragile secondary mechanism that should never be
destructive.

## Thorough solution (permanent, class-wide — not a one-off)

### 1. Fix the journal (eliminates the root cause)

Set `_journal.json` entry 0020 `when` = `0019.when + 1` = **1778976000001**
so the journal is strictly monotonic.

- Stuck DBs (watermark 1778976000000): `1778976000000 < 1778976000001` → true
  → normal `migrate()` applies 0020 → schema correct → `verifySchema()` passes
  → **server self-heals on next start; `fix-db` no longer needed**.
- Fresh installs: whens remain strictly increasing 0–20 → unaffected.
- 0000–0019 unaffected (their when ≤ watermark; not re-applied).
- ENG-009 CI guard unaffected: `db:generate` only appends entries, never
  rewrites an existing `when`; `git diff` stays clean after generate.

### 2. Tolerate duplicate columns on normal startup

Broaden `db/index.ts` `runMigrations` silence regex from
`(table|index) … already exists` to also include `duplicate column name`
(align with `repair.ts` `TOLERATED`). Protects the small set who already ran
`fix-db` and recorded 0020 with the old `when`, so the journal bump cannot
crash their boot on a re-applied `ALTER TABLE … ADD COLUMN`.

### 3. Make `fix-db` position-based (defense-in-depth, future re-alignments)

Replace `repair.ts` per-file-hash full replay with **journal-position prefix
reconciliation** (matches Drizzle's clean-prefix invariant: it inserts exactly
one row per success in order):

- `K = count(__drizzle_migrations)` → journal entries `[0,K)` are already
  applied. Do **not** execute their SQL; normalize their recorded hash to the
  current file hash (hygiene).
- Apply only `[K,N)` with the existing tolerant per-statement logic; insert
  `(hash, when)`.

Robust to both content re-alignment *and* the non-monotonic-`when` defect;
`0006` (idx 6 < K) is never re-run again, for anyone, ever.

### 4. Regression guard

Add a test asserting `_journal.json` `when` is strictly increasing by `idx`.
Catches any future hand-added raw-SQL migration repeating this defect.

## Out of scope

- Rebuilding historical snapshots / rewriting `_journal.json` whens for
  0000–0019 (ENG-009 Scope A stands; only 0020's `when` is corrected).
- Replacing the old deployed launcher binary (separate release concern).
