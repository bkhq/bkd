# ENG-034 Stop probing the Claude CLI on every execution

- **status**: completed
- **priority**: P1
- **owner**: roy
- **createdAt**: 2026-08-30 00:00

## Description

Claude sessions fail with `OAuth session expired and could not be refreshed`.

`executeIssue` calls `executor.getAvailability()` on every run
(`orchestration/execute.ts:55`), and the Claude executor's implementation is
uncached: it spawns `claude --version` and then `claude auth status --json`
(`executors/claude/executor.ts:203-243`). With the default concurrency of 5
(`routes/settings/general.ts:173`), starting a batch puts up to ten CLI processes
on the same `~/.claude/.credentials.json` at once. The stored credential carries an
8-hour access token plus a separately-expiring refresh token, i.e. rotation — so
concurrent refreshes race, all but one get an already-consumed refresh token, and a
loser can write the dead token back, which takes the whole session down until a
re-login.

The probe is also pointless. The guard reads `avail.executable === false`, and no
executor ever sets `executable`: it is declared optional in `types.ts:114` and only
passed through in `virtual-engines.ts:267`. The condition can never be true, so every
execution paid two process spawns and one OAuth touch to evaluate a constant.

`getAvailability()` and the call site both date from the initial commit (`cdcaa8a`),
when auth status was a local `existsSync` check. `df6bd50` (ENG-030, 2026-08-15)
replaced that with the CLI call, on the stated assumption that it runs "only inside
the cached engine probe" — which was already untrue: the same `execute.ts:55` call
exists in that commit's parent.

Acceptance criteria:

- The execution path performs no engine availability probe.
- A test asserts `getAvailability` is not called while executing an issue.
- Engine probing keeps using the cached discovery path (`startup-probe.ts`).

## ActiveForm

Removing the per-execution Claude CLI probe

## Notes

Diagnosed with the user on 2026-08-30.

Completed 2026-08-30. Removed the probe and its dead guard from
`orchestration/execute.ts`; the execution path now spawns no CLI of its own.
Engine availability keeps flowing through `startup-probe.ts`, which is what the
ENG-030 commit assumed was the only caller.

`test/execute-no-probe.test.ts` counts calls to the registered executor's
`getAvailability` across a real execution and asserts zero. Verified it catches the
regression: restoring the probe makes it fail, removing it makes it pass.

Not verified: that `claude auth status --json` itself performs a token refresh. The
access token in this environment was still valid, so running it would have proved
nothing either way. The refresh-race explanation fits the symptom and the rotating
credential structure, but the change stands on its own — two process spawns per
execution to evaluate a condition that can never be true.
