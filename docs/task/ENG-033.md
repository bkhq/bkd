# ENG-033 Stop rendering the CLI activity indicator as chat messages

- **status**: completed
- **priority**: P2
- **owner**: roy
- **createdAt**: 2026-08-26 18:10

## Description

Issue #8 on the production install shows 57 bare `requesting` lines in one turn.
The source envelope carries nothing else:

```json
{"type":"system","subtype":"status","status":"requesting","uuid":"…","session_id":"…"}
```

`parseSystem`'s `case 'status'` puts `data.status` into the message *content*, so
the CLI's activity indicator — the string that drives the spinner label in the
interactive TUI — becomes a chat message. A captured stream shows exactly one per
API request:

```
STATUS:requesting → message_start → assistant … → STATUS:requesting → message_start → …
```

Across the whole production database: `requesting` 3005, `compacting` 299,
`status` 4.

Acceptance criteria:

- `requesting` and the degenerate `status` value are dropped, not persisted.
- `compacting` still surfaces — it is the one value that explains a long pause.
- An unknown future status value still surfaces rather than being swallowed.

## ActiveForm

Filtering the CLI activity indicator out of the chat.

- **blocked by**: (none)
- **blocks**: (none)

## Notes

- Filtering by value rather than suppressing the whole subtype, so a status that
  does carry meaning is not lost with it.
- 2026-08-26 18:10 — Requested directly by the user; implementation started.
- 2026-08-26 18:20 — Implementation and verification completed.
- The fix only stops new rows. The 3005 already in the production database still
  render; clearing them is a separate, operator-owned decision:
  `delete from issues_logs where entry_type='system-message'
   and content in ('requesting','status')
   and metadata like '%"subtype":"status"%';`
