# DEV-004 Upgrade all workspace dependencies to latest

- **status**: completed
- **priority**: P2
- **owner**: cd
- **createdAt**: 2026-09-09

## Goal

Bring every dependency across the monorepo (`@bkd/root`, `@bkd/api`,
`@bkd/frontend`, catalog) up to the latest stable version published on
npmjs.com, verified via `bun outdated --filter '*'` on 2026-09-09.

## Scope

- Minor/patch bumps (37 packages): hono, @hono/zod-openapi, @hono/zod-validator,
  nanoid, @types/bun, zod (catalog), react/react-dom, react-router-dom,
  @tanstack/*, shiki + @shikijs/*, @base-ui/react, @pierre/diffs,
  @codemirror/lang-html, @codemirror/lang-markdown,
  @atlaskit/pragmatic-drag-and-drop-hitbox, dompurify, i18next, react-i18next,
  lucide-react, sonner, zustand, vite, @vitejs/plugin-react,
  @testing-library/react, @types/react, @types/react-dom, shadcn, eslint,
  @antfu/eslint-config, @eslint-react/eslint-plugin, eslint-plugin-react-refresh.
- Major bumps (changelogs verified, see PLAN-020):
  - @atlaskit/pragmatic-drag-and-drop 2 -> 3 (entry-point rename; legacy paths
    kept as deprecated shims, so imports are migrated in the same change)
  - vitest 4 -> 5 (Node 22 / Vite 6.4 minimum; mocks now cleared before each
    test; `sequential` option removed)
  - jsdom 29 -> 30 (Node minimum raised only)
  - @testing-library/jest-dom 6 -> 7 (`toHaveTextContent` is now strict)
  - @libsql/client 0.17 -> 0.18 (dev-only, drizzle-kit driver)
- Major bump, split layout: typescript 6.0.3 -> 7.0.2 in the catalog, consumed
  by `@bkd/api`, `@bkd/frontend` and `@bkd/shared`. `@bkd/root` keeps an
  off-catalog `typescript: ^6.0.3` because typescript-eslint 8.70 (the newest
  published release; no v9 exists) declares `typescript: >=4.8.4 <6.1.0` and
  the v7 package ships the native compiler with no classic JS compiler API.
  Delete the root pin once typescript-eslint supports v7. The CI `Typecheck`
  job moves to per-workspace `typecheck` scripts, otherwise `bunx tsc` at the
  repository root silently keeps using v6.

- CI action pins: `actions/checkout@v6 -> @v7`, `actions/cache@v5 -> @v6`.
  `setup-node@v7`, `upload-artifact@v7`, `download-artifact@v8` and
  `oven-sh/setup-bun@v2` are already on their latest major. With every action
  on a `node24` bundle, `FORCE_JAVASCRIPT_ACTIONS_TO_NODE24` (added by CI-001)
  is dead and is removed from both workflows.
- `node-version: 22 -> 24` in `ci.yml`. Action pins keep the major-only form.
- Stale pins found outside `package.json`: lode v0.1.0 -> v0.3.1 in five
  user-facing places (`README.md`, `README.zh-CN.md`, `docs/deployment.md` x2,
  the release-notes heredoc in `release.yml`) plus `LODE_VERSION`; Bun
  1.4.0 -> 1.4.2 in `docs/bkd.lode.toml` and the mirrored block in
  `docs/deployment.md`.
- Remove `@types/dompurify` — the registry deprecates it as a stub, `dompurify`
  ships its own declarations, and it drags a stale `dompurify@3.4.2` into the
  tree.
- Open decision, see PLAN-020 step 11: whether to move `LODE_VERSION` itself,
  given the unresolved question of whether a lode-cli 0.3.1 signature verifies
  on a v0.1.x-era lode in the field.

## Notes

- 2026-09-09 — Implemented and verified. `bun outdated --filter '*'` now reports
  a single entry, the intentional root `typescript` pin.
- One source change was needed beyond the planned drag-and-drop import
  migration: `@testing-library/jest-dom` 7 no longer augments Vitest's
  `Assertion` from its bare entry point — that path only references `jest.d.ts`.
  `src/test-setup.ts` now imports `@testing-library/jest-dom/vitest`, which
  registers both the matchers and their types. Without it the frontend
  typecheck fails with 27 `TS2339` errors on `toBeInTheDocument` /
  `toBeDisabled`.
- vitest 5's clear-mocks-by-default change caused no fallout; all 13 frontend
  files (96 tests) pass unchanged.
- `bun audit`: 78 advisories before (25 high / 42 moderate / 11 low), 58 after
  (21 high / 32 moderate / 5 low). Every remaining one is transitive under
  `shadcn`, the ESLint plugins, or `@libsql/client`, and none is reachable from
  a direct dependency: the `hono` advisory is `<4.12.21` against our 4.13.7, and
  the `nanoid` one is `<3.3.16` against our 6.0.1. Both are flagged only via
  older copies pulled in by `shadcn` and `postcss`.
- Removing `@types/dompurify` also removed the stale `dompurify@3.4.2` it
  dragged in; the lockfile now resolves exactly one `dompurify`, at 3.4.15.
- `GET /api/settings/workspace-path > returns current workspace path` failed on
  `main` before any bump and was initially left alone as out of scope. Fixed
  afterwards on request: `test/security-filesystem-symlink.test.ts` restored
  `workspace:defaultPath` to `''` in its `afterAll`, while the two sibling
  fixtures (`api-files-upload.test.ts`, `security-fs-hardening.test.ts`) restore
  it to `'/'`. Every consumer of that setting guards on truthiness, so `''` and
  `'/'` behave identically at runtime, but the settings route reads
  `value ?? homedir()` and so reported the stored empty string. The test only
  failed in a full run, never in isolation. Restoring `'/'` like the siblings
  fixes it; API suite is now 637 pass / 1 skip / 0 fail.

- complete: Dependency sweep completed and verified
- 2026-09-09 (follow-up) — Install snippets no longer name a lode version.
  `README.md`, `README.zh-CN.md`, the `docs/deployment.md` quick start and the
  release-notes heredoc in `release.yml` now use
  `https://github.com/dotns/lode/releases/latest/download/lode-linux-x64.tar.gz`,
  which GitHub redirects to the newest release, so they cannot go stale again.
  Three places keep an explicit version on purpose: the production install in
  `docs/deployment.md` section 1 (lode is the trust root of the update path),
  `LODE_VERSION` in `release.yml` (a floating signing tool would make releases
  irreproducible), and the Bun pin in `docs/bkd.lode.toml` (that file states
  runtime downloads are not signature-verified, and `[runtime].version` doubles
  as lode's cache key).
